# Configuration, build and operations

This describes **checked-in behavior** at `16e8c6f`. It is not approval to
deploy, a cloud access runbook or a proposal to replace the backend.

## Current deployment boundary

```text
Local: browser -> Vite -> /api proxy -> existing Python API on port 8080

Build: npm ci -> npm run build
                  prebuild.mjs -> frontend env allowlist
                  tsc -b -> vite build -> dist/

Cloud Build: install -> build -> deploy App Engine ip-react
                                     -> deploy dispatch configuration

Deployed browser: static frontend host + existing /api service routing
```

[app.yaml](../app.yaml) configures App Engine service `ip-react` with runtime
`python312` and static handlers. That runtime declaration does not mean the
React repository contains a Python application or a new backend.
`/assets` serves `dist/assets` with one-year immutable caching; `/favicon.ico`
has a dedicated handler; other service routes return `dist/index.html`.

[dispatch.yaml](../../dispatch.yaml) (project level) sends `/api/ps/*`, `/api/widget/*` and
`/api/act/*` to their corresponding services, and other `/api/*` to `default`.
It does not itself document all frontend domain/traffic routing. Confirm the
actual target host/service and approved routing in the deployment environment.

No FastAPI, Cloud Run, database or IaC implementation is part of this checkout.
Do not treat presentations or work in another checkout as deployed code.

## Configuration

All `VITE_*` values are public build-time browser values. Keep backend secrets
out of them even when the source configuration contains secrets.

| Value | Consumer / source | Default or caveat |
|---|---|---|
| `VITE_API_URL` | Shared Fetch client | `/api` from the committed `.env`; empty prefix if unset; not generated by prebuild |
| `VITE_BUCKET_URL` | Runtime theme-asset loader | `/assets/` fallback |
| `VITE_SITE_TITLE` | Document title | `Insights Portal` fallback |
| `VITE_PORTAL` | Demo auth/nav/portal branches | `SI` fallback, not authorization |
| `VITE_GOOGLE_CLIENT_ID` | Google Slides OAuth | Empty if unavailable |
| `VITE_GOOGLE_API_KEY` | Google SDK initialization | Empty if unavailable; restrict any approved browser API key appropriately |
| `ENV_CONFIG_PATH` | Node prebuild script only | Optional source file path; otherwise frontend-directory `env-config.json` |

[prebuild.mjs](../scripts/prebuild.mjs) reads per-BU config and emits:

| Source field | Generated browser field |
|---|---|
| `BUCKET_URL` | `VITE_BUCKET_URL` |
| `SITE_TITLE` | `VITE_SITE_TITLE` |
| `PORTAL` | `VITE_PORTAL` |
| `GCP_CLIENT_ID` | `VITE_GOOGLE_CLIENT_ID` |
| `GCP_API_KEY` | `VITE_GOOGLE_API_KEY` |

It normalizes a trailing bucket slash and writes `.env.production.local`.
Unreadable/invalid configuration or absent values currently log a message and
use defaults. This is existing build behavior, not evidence that the correct
BU is configured. Do not print decrypted file contents to diagnose it.

The repository-root `.gitignore` excludes `env-config.json`, `dist/`,
`coverage/` and environment files such as `.env.local` and
`.env.production.local`, except the public frontend `.env` and the safe
`.env.example`. Keep local values uncommitted. Vite mode-specific and
process-environment precedence matters; see
[development](development.md#environment-and-build-behavior).

## Build and preview

```bash
npm ci
npm run build
npm run preview
```

`npm run build` automatically invokes `prebuild`, then `tsc -b && vite build`.
The generated frontend values are fixed into the bundle; changing a runtime
shell variable after deployment does not rewrite it. Preview serves `dist/`
without a configured API proxy; verify API routing independently.

The current build reports a large-chunk warning. A successful build establishes
types/bundling, not runtime performance, identity, correct branding, backend
availability or real export success. Do not silence the warning as a substitute
for measuring and reviewing an optimization.

## Cloud Build and the KMS workaround

Repository-root [cloudbuild.yaml](../../../../cloudbuild.yaml) installs with
Node 22 and runs the frontend build in `projects/wiq-si-portal/frontend`,
deploys that directory's `app.yaml`, then deploys project-level shared
`dispatch.yaml`. Encrypted per-BU configs live in `projects/wiq-si-portal/configs`;
see the [project guide](../../README.md#build-and-deployment). It does not
currently run tests, coverage or lint.

**Config decryption is temporarily commented out** because the build service
account lacks KMS decryption permission. The build currently waits on install
only; fresh builds without another config source use bundled defaults and no
Google Slides client values from decrypted configuration.

Restoring per-BU decryption requires approved key/service-account permission,
the correct encrypted config mapping, and restoration of both the
`decrypt-config` step and build dependency. Validate without exposing secrets.
Do not bypass KMS with a plaintext committed file or grant broad permissions
as an incidental frontend change.

## External assets and integrations

`applyThemeAssets` injects the configured `env.css`, favicon and touch icon,
and sets the document title. `index.html` loads hosted icon fonts and GTM.
Slides loads Google SDKs and needs OAuth plus backend image endpoints.

Browser tests with blocked hosts cannot establish visual or analytics/export
acceptance. Confirm approved hosts, fonts, icons, theme availability and
configuration for the target BU. Check cache headers for non-fingerprinted
theme assets as well as hashed bundles; a cached theme can mask a deployment
change.

## Release checklist

This is a checklist for an authorized owner, not an instruction to run a
production deployment:

1. Record approved frontend/backend source versions, target service/environment,
   BU configuration and accepted scope; identify remaining migration gaps.
2. Run tests/coverage/build against the actual merged candidate; do not rely
   on Cloud Build to enforce checks it does not contain.
3. Confirm real identity/roles, permitted hierarchy and API dispatch/session
   behavior. Demo portal configuration cannot authorize a user.
4. Validate deep links/reloads, correct API Content-Type, theme/font loading,
   mobile boundaries and required external integrations in staging.
5. Confirm the KMS workaround's effect and whether default configuration is
   acceptable for that environment. Do not treat defaults as silent success.
6. Obtain rollout/traffic and shared-dispatch approval, identify the previous
   known-good frontend version and record a rollback procedure.
7. After release, check browser/runtime and API errors, assets, relevant
   analytics/actions and agreed parity cases without unapproved mutations.

## Rollback and recovery

Before rollout, identify the previous approved App Engine version and how the
environment owner restores traffic. Confirm that its static bundle/config is
still available and compatible with the unchanged backend contracts.

Dispatch changes and identity/theme configuration may need independent
restoration; rolling back frontend traffic alone does not undo shared routing.
Do not prescribe or run a generic destructive Git reset or cloud deployment as
a rollback. Preserve commits/evidence, involve the environment owner and verify
deep links, sessions and API paths after the approved recovery.

For local symptoms see [troubleshooting](development.md#troubleshooting).
Record operational findings without tokens, raw business data or decrypted
configuration.
